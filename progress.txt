## Codebase Patterns
- Vitest config lives in `vite.config.ts` under `test` key; e2e tests excluded via `exclude: ['tests/e2e/**']`
- Unit tests go in `tests/unit/`, e2e tests in `tests/e2e/`
- Playwright uses chromium only, dev server auto-started via `webServer` config
- TypeScript strict mode enabled in `tsconfig.app.json`
- Scoring library lives in `src/scoring/` with barrel export via `index.ts`
- Test fixtures for poses go in `tests/unit/scoring/fixtures.ts` — use `makePose()` helper for partial keypoint data
- Pose estimation module lives in `src/pose/` with barrel export via `index.ts`
- TF.js MoveNet uses `@tensorflow-models/pose-detection` — must stub `@mediapipe/pose` via Vite resolve alias (see `src/stubs/mediapipe-pose.ts`)
- Sample dance pose JSON lives in `public/dances/sample-dance.json` — generated by `scripts/generate_sample_dance.py`
- App uses simple state-based routing (no router lib) — `view` state switches between 'home' and 'dance'
- Vitest environment is `node` — cannot use `document.createElement` in unit tests; use plain object simulation instead
- DanceMode has a `ready` phase between `loading` and `countdown` to ensure user interaction for autoplay with audio
- React components go in `src/components/`
- Python pipeline lives in `scripts/` with own `requirements.txt`; tests via `python scripts/test_schema.py`
- Backend server lives in `server/` — `app.ts` exports Express app (for testing), `index.ts` starts the listener
- Backend tests use `supertest` to test Express routes without starting the server
- `npm run dev` uses `concurrently` to run frontend (Vite) and backend (tsx watch) together
- Backend uses `tsx` for TypeScript execution (no compile step needed)
- `.env` support via `dotenv` — `.env.example` has documented defaults
- Backend routes organized in `server/routes/` — imported and mounted in `server/app.ts`
- Job manager (`server/jobs.ts`) is in-memory — use for async processing tracking
- Processing pipeline (`server/processing.ts`) shells out to yt-dlp, ffmpeg, and Python scripts
- Processed dance data stored in `data/dances/{jobId}/` (video.mp4, audio.mp3, poses.json, thumbnail.jpg)
- SQLite database via `better-sqlite3` — `server/db.ts` exports CRUD functions, DB auto-creates at `data/groovy.db`
- DB path configurable via `DB_PATH` env var — tests use unique temp DB files to avoid cross-test contamination
- `getDb()` reads `DB_PATH` from env at call time (not module load) — needed for test isolation
- Delete dance route cleans up associated files (video, audio, poses, thumbnail) from disk
- File serving routes (/:id/video, /:id/audio, etc.) use fs.createReadStream for streaming; video/audio support Range requests for seeking
- Webcam recording uses a hidden composite canvas (webcam + skeleton) captured via `captureStream(30)` → MediaRecorder
- Sessions stored in SQLite `sessions` table with foreign key to `dances`; CRUD in `server/db.ts`
- Session routes in `server/routes/sessions.ts` — file uploads via multer
- Session files stored in `data/sessions/{timestamp-random}/` (recording.webm, poses.json)
- All e2e tests that hit `/` must mock `**/api/dances` GET to avoid backend dependency
- YouTube thumbnails: `https://img.youtube.com/vi/{videoId}/mqdefault.jpg` — no backend serving needed
- API dance IDs prefixed with `api-` to distinguish from bundled dance IDs in frontend
